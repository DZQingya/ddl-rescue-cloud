# DDL 急救站业务规则文档

## 1. 适用范围与数据约定

本文定义 DDL 急救站的时间容量、任务优先级、排期、冲突检测和风险生成规则。大模型只负责抽取作业信息并输出 JSON；优先级计算、容量计算、排期、冲突检测和可行性判定均由确定性规则完成。

- 所有时长均以分钟为单位。
- `deadline.normalized` 应包含时区；排期日期按该时区解释。
- `plan.days[].date` 使用 `YYYY-MM-DD`，`plan.days[].tasks` 存放任务 ID。
- 任务预计工时取 `tasks[].estimate_min`。本版不拆分任务，只有当完整任务工时可安排时才排入日期。
- `minimum` 是保底任务，`advanced` 是进阶任务，`challenge` 是挑战任务。
- 单条任务可带自己的 `deadline` 对象和 `ddl_id`；根 `deadline` 是所有 DDL 中的最早截止时间。
- 时间容量、优先级和排期窗口均为可配置规则，不由大模型临时决定。

### 1.1 一条通知中的多个 DDL

通知抽取若识别出多项作业，应先保留为 `ddl_items`，每项包含稳定的 `id`、标题、独立 `deadline`、交付物、材料、风险和任务。规则层的 `aggregate_notification` 将这些项目合并为一个计划对象：

- 输出 `deadlines` 数组，按 DDL ID 保存每项作业的截止元数据。
- 将所有 DDL 的任务合并进根级 `tasks`，每项任务保留 `ddl_id` 和任务级 `deadline`。
- 同一通知的多个任务 ID 若重复，聚合时加上 DDL ID 前缀，并同步改写该 DDL 内的依赖引用。
- 根级 `deadline` 设为所有 DDL 截止时刻中的最早值，供旧调用方兼容；排期与优先级实际使用各任务自己的截止时间。
- 交付物、材料和风险合并保留，不因遇到第一个 DDL 就丢弃后续 DDL。

聚合后的数据形状：根 `deadlines` 保存 DDL 列表，根 `tasks` 保存跨 DDL 合并后的任务列表；任务中的 `ddl_id` 关联 DDL，任务级 `deadline.normalized` 是排期边界。输入形式为 `ddl_items: [{id, title, deadline, tasks, deliverables, materials, risks}]`。

## 2. 时间容量配置

### 2.1 默认参数

| 参数 | 默认值 | 含义 |
|---|---:|---|
| `weekday_capacity_min` | 120 分钟 | 周一至周五每天默认可用于学习的时间。 |
| `weekend_capacity_min` | 180 分钟 | 周六、周日每天默认可用于学习的时间。 |
| `planning_window_days` | 7 天 | 默认纳入排期的截止日前窗口长度。 |
| `capacity_timezone` | 截止时间所带时区 | 用于确定日期、工作日/周末及日容量。 |

以上时长是系统默认值，并非对学生实际空闲时间的判断。实现时应允许通过配置文件、环境配置或用户设置修改这些参数。

### 2.2 容量计算

1. 每项任务的有效排期窗口从“当前日期”和“该任务截止日期前 `planning_window_days` 天”两者中较晚者开始，至该任务截止日期结束。
2. 周一至周五使用 `weekday_capacity_min`，周六、周日使用 `weekend_capacity_min`。
3. `plan.capacity_min` 为所有任务排期窗口按日期去重后、各日期可用分钟的总和。
4. 当前 Schema 没有单日容量覆盖字段，本版只使用全局默认值。
5. 截止日只允许在截止时刻之前安排任务。没有日内时段配置时，容量估算可使用截止日默认容量；但任何任务都不得排到截止时间之后，且须保证任务可在截止时刻前完成。
6. 若当前时刻已达到或超过截止时间，则剩余容量为 0，不生成截止时间之后的排期。

## 3. 任务优先级打分

### 3.1 输入值

- `remaining_min`：从规则计算时刻到截止时间的剩余分钟数，最小取 0。
- `estimate_min`：任务预计工时。
- `level`：任务层级。
- `task.deadline.normalized`：任务自身的截止时间；未提供时通过 `ddl_id` 关联 `deadlines`，再回退到根 `deadline`。

### 3.2 时间紧迫度分数

| 距截止剩余时间 | 分数 |
|---|---:|
| 小于或等于 1 天 | 100 |
| 大于 1 天且小于或等于 3 天 | 80 |
| 大于 3 天且小于或等于 7 天 | 60 |
| 大于 7 天且小于或等于 14 天 | 35 |
| 大于 14 天 | 15 |

### 3.3 工时分数

| `estimate_min` | 分数 |
|---|---:|
| 大于或等于 180 分钟 | 100 |
| 大于或等于 90 且小于 180 分钟 | 75 |
| 大于或等于 45 且小于 90 分钟 | 50 |
| 小于 45 分钟 | 25 |

### 3.4 计算与排序

基础分数：

> `base_score = 0.6 × 时间紧迫度分数 + 0.4 × 工时分数`

层级加分：

| `level` | 加分 |
|---|---:|
| `minimum` | +30 |
| `advanced`（进阶） | +10 |
| `challenge`（挑战） | +0 |

> `priority_score = base_score + level_bonus`

调度时先按层级分阶段：`minimum`、`advanced`（进阶）、`challenge`（挑战）。同一层级内先按任务截止时刻从早到晚排序，再按 `priority_score` 降序；分数相同时，预计工时较长者优先；仍相同时按任务 ID 字典序排列，确保结果可复现。任务依赖关系优先于同层级内的普通排序：前置任务必须先安排。

## 4. 排期规则

### 4.1 排期窗口与边界

1. 默认在每个任务自身截止日前 7 天的窗口中安排；如果当前日期已进入该窗口，从当前日期开始。
2. 不得将任务排到该任务截止时间之后。
3. 不得安排在有效窗口开始之前。
4. 每个任务不得重复安排。若任务依赖尚未安排或未完成，不得安排其后续任务。

### 4.2 层级优先

1. 先尽可能排入全部可完成的 `minimum` 任务。
2. 所有 `minimum` 任务都成功排入计划且仍有容量，才开放 `advanced`（进阶）任务。
3. 所有 `minimum` 与 `advanced`（进阶）任务都成功排入计划且仍有容量，才开放 `challenge`（挑战）任务。
4. 任一 `minimum` 因工时超过单日容量、依赖未满足或其他硬约束无法排入时，停止后续层级排期；将计划判为不可行，生成 high 级别 `conflict` 风险并触发 Rescue Mode。
5. 任一 `advanced`（进阶）任务无法排入时，不安排 `challenge`（挑战）任务；将计划判为不可行，生成 high 级别 `conflict` 风险，建议砍减进阶任务范围，并触发 Rescue Mode。
6. 每项任务须以完整 `estimate_min` 放入某日剩余容量；本版不跨日拆分。

### 4.3 尽量分散任务

1. 尽量将任务分散在有效排期窗口内，避免集中到临近截止的少数日期。
2. 在同层级、同优先级的可选日期中，优先选择当前已排工时较少且能完整容纳任务的日期。
3. 若日期负载相同，优先选择较早日期。
4. 分散安排不得违反优先级阶段、依赖、每日容量及各任务截止时间约束。
5. 若没有任一日期能容纳完整任务，则该任务不排入计划，并在风险中说明原因。

### 4.4 每日输出

- `plan.days` 按日期升序排列。
- 每个日期的 `tasks` 按该日实际安排顺序保存任务 ID。
- 不产生空日期记录。

## 5. 冲突与过载判定

### 5.1 单日过载

对每个日期计算已排任务的预计总工时：

> `day_required_min = 当日已排任务 estimate_min 之和`

若 `day_required_min > day_capacity_min`，则判定该日过载，并生成 `type="conflict"` 风险。风险消息应包含日期、需求工时和可用容量。

正常排期不应超出每日容量，因此此风险通常表示计划被修改、容量配置变更或现有排期数据不符合规则。应在最终计划生成后再次检查。严重度默认 `high`；若确定性重排可以消除问题，则重排后不保留已解决的过载风险。

### 5.2 全局不可行

计算本次计划范围内全部待完成任务总工时 `total_required_min`，以及截止前总可用分钟 `total_capacity_min`。

若：

> `total_required_min > total_capacity_min`

则：

- 设置 `plan.feasible = false`。
- 生成 `type="conflict"` 风险，说明需求工时、可用容量及缺口。
- 触发 Rescue Mode。
- 仍安排所有可以合法放入窗口的任务；不得超每日容量或越过截止时间。

若总需求不超过总容量，容量层面可行；但若依赖关系或任务不可拆分等约束导致任务无法合法安排，则仍须将 `plan.feasible` 设为 `false`。

### 5.3 Rescue Mode

Rescue Mode 是确定性排期规则下的容量不足处理状态，不代表额外的大模型调用。触发后：

1. 优先安排 `minimum` 任务，并遵守同层级优先级和依赖顺序。
2. 只要仍有 `minimum` 未排入，不安排 `advanced`（进阶）或 `challenge`（挑战）任务。
3. 只要仍有 `advanced`（进阶）未排入，不安排 `challenge`（挑战）任务。
4. 保持每日容量与截止时间硬约束。
5. 对未排任务不伪造 `plan.days` 项；在 `conflict` 风险消息中说明未安排数量或原因。
6. 不因进入 Rescue Mode 自动放宽时间容量或依赖约束。

## 6. 风险生成条件

所有风险都应填写 Schema 要求的 `type`、`message`、`severity`。消息应具体说明问题及其对排期的影响。同一原因避免重复生成相同风险。

### 6.1 `ambiguity`（信息歧义）

在信息存在多种合理解释、影响任务拆分或排期时生成，例如：

- “下周五”等相对时间缺少可靠采集时间或时区，无法唯一标准化。
- `deadline.normalized` 与原文或 `source_span` 不一致。
- `deadline.confidence` 低于配置阈值；建议默认 `0.70`，由代码配置调整。
- 作业要求、交付物、任务内容或依赖关系有多种解释，且会改变计划。
- 缺少可靠信息，无法估计任务工时或确定可执行步骤。

严重度建议：可能导致错过截止或漏交关键成果为 `high`；需要确认但可暂拟计划为 `medium`；影响较小为 `low`。

### 6.2 `conflict`（容量或排期冲突）

在出现以下情况时生成：

- 某日已排任务总工时大于当日可用容量。
- 截止前全部待完成任务总工时大于截止前总可用分钟。
- 任务被安排在截止时间之后。
- 任务顺序违反依赖关系。
- 任务工时或容量配置变化后，既有计划不再满足每日容量约束。
- 任务无法完整放入任何有效日期，或因其他硬约束无法安排。

其中，全局需求超过总容量时必须令 `plan.feasible=false` 并触发 Rescue Mode。若重排后冲突已消除，不保留已解决冲突的风险记录。

### 6.3 `missing_material`（缺少材料）

在已明确知道某材料必需、但材料未提供或不可用时生成，例如：

- 作业要求使用文件、教材、数据集、模板、链接或工具，但 `materials` 中缺失。
- 材料只以“老师发的文件”等模糊名称记录，无法定位或获取。
- 某任务依赖的材料尚未收到、无法访问或未确认可用。
- 交付物或执行步骤明确依赖材料，但材料列表为空或不完整。

如果不确定材料是否必需，生成 `ambiguity`；若已确认必需但缺失，生成 `missing_material`。两个条件同时成立时可分别记录，并各自说明事实。

## 7. `plan` 字段填写规则

| 字段 | 填写规则 |
|---|---|
| `plan.capacity_min` | 有效排期窗口内、截止时刻前的可用容量总和。 |
| `plan.required_min` | 本次纳入计划的待完成任务预计工时总和。 |
| `plan.feasible` | 全部任务可在容量、依赖和截止时间等约束内完成时为 `true`；否则为 `false`。 |
| `plan.days` | 按日期升序保存每日已排任务，任务以 ID 引用。 |

`plan.feasible` 表示基于当前容量参数和任务估时的计划可行性，不代表学生已完成任务。任务状态由应用状态管理流程维护。
